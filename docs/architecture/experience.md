# Архитектура хранения и обработки пользовательского опыта

## Цель

Поддерживать несколько специализаций одного пользователя при единой базе фактического опыта. Опыт адаптируется под вакансии, но основной проверенный опыт не изменяется агентом без подтверждения пользователя.

## Уровни данных

```text
ExperienceBase → SpecializationProfile → JobRequirements → JobApplicationProfile → GeneratedResume
```

- `ExperienceBase` — единый набор подтверждённых фактов.
- `SpecializationProfile` — производное представление опыта под роль.
- `JobApplicationProfile` — версия под конкретную вакансию с локальными переопределениями.

## Каноническая модель

Основным объектом должен быть не готовый текст резюме, а набор фактов:

```text
User
 └── ExperienceBase
      ├── Employment: company, position, period
      ├── Projects
      ├── Responsibilities
      ├── Technologies
      ├── Skills
      ├── Achievements
      ├── Education
      └── Certifications
```

Каждый факт хранит происхождение, доказательства, статус проверки и связь с проектом.

```json
{
  "id": "exp-123",
  "company": "Компания",
  "position": "Backend Developer",
  "period": { "from": "2021-03", "to": "2024-06" },
  "projects": ["project-1"],
  "technologies": ["Python", "FastAPI"],
  "verificationStatus": "verified",
  "verifiedBy": "user",
  "verifiedAt": "2026-09-24"
}
```

Агент не меняет `ExperienceBase` напрямую. Он создаёт предложение, пользователь подтверждает, исправляет или отклоняет его, после чего создаётся новая версия. Старые версии сохраняются; удаление реализуется как `deprecated`.

## Факт, доказательство, формулировка и профит

Их нужно хранить отдельно:

1. Факт: что действительно сделал пользователь.
2. Доказательство: исходный документ, проект, комментарий пользователя или другой источник.
3. Профессиональная формулировка: как факт описывается в резюме.
4. Результат: какой эффект получен.

Статусы результата:

```text
confirmed  — подтверждён пользователем
calculated  — рассчитан на основании данных
estimated   — оценён пользователем
qualitative — описан без числового показателя
unknown     — результат не установлен
```

Профит нельзя выдумывать. Агент должен выяснять масштаб, исходное состояние, затраченное время, объём данных и изменения в скорости, стоимости, стабильности, конверсии или количестве ошибок.

## Структура задачи

```text
Задача
 ├── Контекст
 ├── Действие пользователя
 ├── Инструменты и технологии
 ├── Масштаб
 ├── Ограничения
 ├── Результат
 └── Доказательства
```

Один проект может использоваться в нескольких специализациях. Связи между проектами, задачами, технологиями и достижениями должны быть много-ко-многим.

## Профили специализаций

Специализация — конфигурация отбора и приоритизации, а не копия опыта:

```json
{
  "id": "profile-python-backend",
  "name": "Python Backend Developer",
  "targetRoles": ["Python Developer", "Backend Engineer"],
  "preferredSkills": ["Python", "FastAPI", "PostgreSQL"],
  "priorityProjects": ["project-1", "project-4"],
  "visibilityRules": { "show": ["backend", "api"], "hide": ["manual-testing"] }
}
```

Профиль может менять порядок, видимость, summary, заголовок и акценты, но не исходные факты.

## Версия под вакансию

```json
{
  "id": "application-456",
  "jobId": "job-789",
  "baseProfileId": "profile-python-backend",
  "overrides": {
    "headline": "Senior Python Backend Engineer",
    "prioritySkills": ["Python", "FastAPI", "AWS"],
    "selectedProjects": ["project-1", "project-4"]
  }
}
```

Разрешены только изменения представления: заголовок, порядок, видимость, выбор проектов, подтверждённые формулировки и сопроводительное письмо.

Запрещено добавлять неподтверждённые технологии, менять даты, компании или должности, придумывать метрики, повышать уровень навыка или удалять факт из основной базы.

## Контроль достоверности

```text
draft        — извлечено агентом, не проверено
needs_review — требует уточнения
confirmed    — подтверждено пользователем
rejected     — отклонено пользователем
deprecated   — ранее подтверждено, но больше не используется
```

Для навыка следует хранить уровень, период применения, последний год использования и связанные проекты. Рекомендуемые уровни: `knowledge`, `used`, `advanced`, `expert`.

## Процесс агента

### Первичная загрузка

1. Распознать документ.
2. Извлечь факты, технологии, задачи и результаты.
3. Объединить дубликаты и найти противоречия.
4. Сформировать уточняющие вопросы.
5. Получить подтверждение пользователя.
6. Создать новую версию основной базы.

### Уточнение проекта

Выяснить: что сделал пользователь лично, какие инструменты применял, какой был масштаб, какие ограничения существовали, что изменилось и есть ли измеримый результат.

### Подготовка под вакансию

1. Извлечь требования вакансии.
2. Сопоставить их с подтверждёнными фактами.
3. Найти пробелы.
4. Выбрать релевантные проекты.
5. Предложить формулировки.
6. Показать изменения пользователю.
7. Сгенерировать версию резюме.

## Архитектурные инварианты

```text
ExperienceBase изменяется только после действия пользователя.
Агент может создавать только предложения.
GeneratedResume воспроизводим из исходных данных.
JobApplicationProfile не может изменять ExperienceBase.
Каждая формулировка имеет происхождение и статус проверки.
Удаление факта не уничтожает историю.
```

## Техническая реализация

- PostgreSQL — структурированные данные и связи.
- Объектное хранилище — исходные PDF, DOCX и другие документы.
- Полнотекстовый поиск или vector index — поиск релевантного опыта.
- JSONB — гибкие структуры задач, доказательств и результатов.
- Версионирование — история изменений.
- Аудит — действия агента и пользователя.

Основные сущности: `users`, `experience_bases`, `experience_versions`, `employment_records`, `projects`, `tasks`, `achievements`, `skills`, `technologies`, `evidence_sources`, `specialization_profiles`, `job_descriptions`, `job_applications`, `generated_documents`, `review_tasks`, `audit_events`.

## Главный принцип

**Основной технический опыт — это подтверждённый граф фактов, а резюме — только одно из его представлений.**
