# План реализации UX профилей и черновиков

План покрывает API, схему хранения и поведение интерфейса во всех окружениях.
Docker dev используется как локальная среда проверки persistence-сценариев,
не как область действия требования. Реализация выполняется в текущей рабочей
копии, сохраняя все уже имеющиеся изменения.

## Ограничения

- «Проверено» означает просмотр; при любой сохранённой правке статус сбрасывается.
- Прогресс переноса в базу отображается отдельно от состояния проверки.
- Имя кандидата и типизированные контакты принадлежат общей базе кандидата.
- Контакты, обнаруженные внутри нераспознанного текста импорта, предлагаются
  к переносу в общую базу кандидата; исходный текст черновика сохраняется.
  Перенос требует явного выбора пользователя и виден во всех профилях.
- Проверить и исправить сохранение сквозным сценарием в запущенном Docker dev:
  импорт/правка → явное сохранение → переход/перезагрузка → повторное открытие.
- В форме черновика всегда понятно, сохранён ли он; после правки явная кнопка
  «Сохранить черновик» доступна и сохраняет название и все изменённые блоки.
- Генерация готового документа и общий перенос произвольного текста черновика
  в базу кандидата не добавляются. Исключение: отдельные контактные значения
  после явного подтверждения, как описано ниже.
- Для изменённых сценариев добавить регрессионные проверки; сохранение и
  импорт контактов дополнительно проверить в Docker dev.
- Ни в одном окружении в пользовательских маршрутах не показывать фиктивные
  имена, факты, контакты, вакансии или источники. Fixture-данные разрешены
  только в тестах; пустая БД отображается пустым состоянием.
- После успешной аутентификации пользователь сразу может задать/изменить
  своё имя и общие контакты; наличие загруженного черновика не является
  условием доступа к этим данным.

## Этапы

1. **Backend persistence и API:** добавить название черновика, состояние
   проверки и время обновления; мигрировать существующие строки с сохранением
   владельца, содержимого и доступности; включить reviewed в список; добавить
   обновление названия и общий owner-scoped API имени кандидата/контактов.
2. **Статусы и сохранение:** при изменении названия/блока/добавлении опыта
   сбрасывать reviewed; отделить статус проверки от вычисляемого прогресса
   переноса по существующим DraftApplication; возвращать метаданные в DTO.
3. **Frontend маршруты и список:** переименовать «Профили резюме» в
   «Профили специализации», добавить «Черновики резюме» в навигацию и маршрут;
   показывать название, даты, локальные статусы и фильтры; дать явное
   переименование и повторное открытие.
4. **Frontend редактор:** отдельные широкие карточки блоков, редактируемое
   название, явное сохранение с состояниями/повтором, подтверждение проверки,
   предупреждение о несохранённых данных; сохранить возможность нескольких
   карточек опыта.
5. **Профиль и документация:** показать «Имя пользователя», «Контакты» и
   «Обо мне» с общей моделью данных; обновить инструкции/API/архитектуру,
   REQ-057–REQ-062 и прогресс; выполнить frontend build, миграционный и
   Docker smoke check, `scripts/check_docs.py`, если доступные инструменты это
   позволяют.
6. **Контакты в нераспознанном импорте:** находить контактоподобные значения
   в `unparsed` блоках без удаления исходного текста; показывать кандидатов
   (тип и значение) для подтверждения; по выбору пользователя создавать
   типизированные записи CandidateBase. Проверить отображение тех же записей
   в каждом профиле и защиту от повторного добавления.
7. **Надёжное сохранение и сквозная проверка:** обеспечить явное сохранение
   изменённого названия и всех блоков одной подтверждаемой операцией (один
   backend endpoint/транзакция либо эквивалент без частичного статуса
   «Сохранено»). Убедиться, что актуальный frontend image запущен, кнопка
   доступна на `/resume-drafts`, после успешного сохранения данные остаются
   после навигации и перезагрузки. Зафиксировать сценарий в автоматической
   проверке и проверить его в Docker dev.
8. **Страница основного профиля:** убрать фиктивный `Example Person` из
   пользовательского сценария и убрать все fixture-факты из `/profile`;
   подключить страницу к фактическим данным кандидата и показывать пустое
   состояние вместо вымышленных записей. Сразу после входа дать редактировать
   имя и общие контакты CandidateBase. Имя — отдельные личные данные, а не
   факт опыта. Объяснить факт как утверждение для будущего резюме; источник
   использовать для проверки происхождения, показывать понятной подписью и
   не предлагать пользователю редактировать технический provenance.
9. **Все окружения без фиктивных данных:** убрать все runtime imports
   `services/fixtures`, выставить пустые или явно неподключённые состояния для
   источников, поиска, вакансий и откликов без backend-интеграции; исключить
   демонстрационные записи из production bundle и проверить bundle scan.

## Review focus

- Старые и проверенные черновики остаются доступны после миграции и в общем
  списке; чужие записи не выдаются.
- Смена заголовка или содержимого у reviewed сбрасывает статус проверки.
- Применение блока не меняет review status; его прогресс показывается отдельно.
- Контакты читаются из CandidateBase и изменение видно каждому профилю.
- Ошибка запроса сохраняет введённые значения в форме и не показывает
  ложный статус «Сохранено».
- Сохранение нескольких изменённых полей не оставляет пользователю
  неоднозначный результат при частичном сбое API.
- Контакты из нераспознанного блока не исчезают из текста и не попадают в
  общую базу до подтверждения; подтверждённые контакты общие для профилей.
- Dev smoke проверяет актуальность frontend контейнера и сохранение после
  повторного открытия черновика.
- `/profile` показывает настоящее имя из CandidateBase или ясное пустое
  состояние; демонстрационное имя не выглядит как данные пользователя.
- После авторизации имя и контакты читаются/сохраняются через CandidateBase
  до и после импорта черновика; тестовые данные остаются только в тестах.
- Страница отличает значение факта от происхождения; технический provenance
  не предлагается редактировать как обычный текст.
