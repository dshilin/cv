# ТЗ на исправление работы с профилями и черновиками резюме

## 1. Цель

Сделать понятным полный путь черновика резюме: пользователь отличает профиль
специализации от документа резюме, находит черновик после перехода на другую
страницу или перезапуска приложения, понимает, сохранены ли изменения, и
может явно отметить черновик проверенным, не путая проверку с переносом данных
в общую базу кандидата. Профиль специализации должен также содержать
самостоятельные блоки «Имя пользователя», «Контакты» и «Обо мне».

Это ТЗ дополняет [SPEC-005](2026-09-25-resume-profile-backend-design.md):
оно сохраняет его правила опыта, выбора фактов и жизненного цикла, но описывает
недостающие данные имени кандидата, пользовательский интерфейс профиля и
API/метаданные/список черновиков.

## 2. Основание и текущее поведение

Основание — вопросы и уточнения пользователя в чате 2026-09-28: различие
«профиля» и «резюме», поиск черновика после ухода со страницы, явное понимание
сохранения, управление статусом и отдельные читаемые карточки нескольких
блоков опыта.

Проверка текущего кода на 2026-09-28 выявила следующее:

- `ResumeDraftModel` хранит черновик в backend-БД; создание, импорт и изменение
  блока завершаются commit. В Docker dev используется SQLite volume
  `cv_profiles_data`. Переход между frontend-маршрутами сам по себе не удаляет
  черновик.
- Frontend загружает список только на странице `/resume-profiles`. В боковой
  навигации нет отдельного раздела черновиков, поэтому после ухода черновик
  нельзя найти из других разделов приложения.
- Строка списка содержит только первые восемь символов UUID и техническое
  имя статуса. У модели есть дата создания, но список API её не возвращает;
  у черновика нет пользовательского названия.
- `GET /api/v1/resume-drafts` исключает `reviewed`. Проверенный черновик
  сохраняется в БД, но исчезает из обычного списка. Отдельного списка,
  фильтра или маршрута для него во frontend нет.
- Редактирование блока отправляется при потере полем фокуса. Видимого
  состояния «сохраняется / сохранено / ошибка сохранения» нет. Отдельной
  команды сохранения и кнопки проверки во frontend нет, хотя backend endpoint
  `POST /resume-drafts/{draft_id}/review` существует.
- «Профили резюме» фактически содержит специализационные профили (например,
  «AI Engineer») и импортные черновики. Сам документ резюме, сформированный
  для профиля, на этой странице не создаётся.
- В редакторе профиля доступны только название специализации и заголовок
  резюме. Backend уже имеет профильное поле `summary`, но отдельные блоки
  имени кандидата и контактов во frontend/API профиля не представлены. Общая
  база кандидата умеет хранить контактные записи, но UI профиля их не показывает.
- Повторный вызов API добавления опыта создаёт новый блок. Интерфейс должен
  явно показывать, что действие можно повторять; каждый сохранённый блок
  опыта редактируется отдельно. Это продолжает REQ-056.

Таким образом, код указывает на проблему обнаружения и идентификации, а не
на удаление черновика при смене страницы. Проверенные черновики — отдельный
случай фактической недоступности в интерфейсе из-за фильтра API.

## 3. Термины интерфейса

- **Общая база кандидата** — факты и записи опыта, которые пользователь
  включает отдельным действием.
- **Профиль специализации** — набор настроек и выбранных записей общей базы
  для направления/роли, например «AI Engineer».
- **Резюме** — документ, сформированный на основе общей базы и профиля
  специализации. Генерация такого документа не входит в текущую реализацию.
- **Черновик резюме** — сохранённые после ручного создания или импорта
  редактируемые блоки. Черновик сам по себе не меняет общую базу и профиль.

В навигации и заголовке страницы следует использовать «Профили
специализации». Раздел черновиков должен называться отдельно — «Черновики
резюме». В интерфейсе не называть профиль готовым резюме и не обещать
генерацию документа, пока соответствующая функция не реализована.

### 3.1 Личные разделы профиля

В профиле специализации добавить три отдельные карточки:

1. **Имя пользователя** — имя человека, которое будет показано в резюме;
   это не название специализации и не имя учётной записи.
2. **Контакты** — отдельные контактные значения с подписью типа (например,
   электронная почта, телефон, ссылка), а не одно безымянное поле.
3. **Обо мне** — отдельный редактируемый текст профиля; он соответствует
   существующему в backend полю специализации `summary`.

По ответу пользователя в чате 2026-09-28 имя означает имя кандидата, которое
показывается в резюме, а контакты являются общими данными кандидата из общей
базы. Ни имя, ни контакты не являются реквизитами учётной записи VK. Они
отображаются в профиле отдельно от названия специализации и сохраняются
независимо от черновика. Это решение закрывает Q-012.

## 4. Предлагаемое поведение

### 4.1 Поиск и идентификация черновика

1. Добавить доступный из постоянной боковой навигации пункт «Черновики
   резюме» и отдельный список/маршрут. Возврат к странице черновиков после
   просмотра другого раздела должен снова загружать данные из backend.
2. По умолчанию показывать все не удалённые черновики, включая `reviewed`.
   Предусмотреть фильтры «Все», «Нужно проверить» и «Проверено»; при наличии
   перенесённых данных отдельно отображать прогресс переноса.
3. У каждого черновика должно быть сохраняемое пользовательское название.
   При создании/импорте выдавать различимое название по умолчанию с датой и
   временем; пользователь может переименовать его. Не сохранять исходный
   файл после импорта ради получения названия.
4. В списке показывать название, дату создания, последнее сохранение и
   понятные статусы. Не использовать короткий UUID или имена enum как главное
   название; технический ID оставить только в диагностике при необходимости.
5. Список упорядочивать по последнему изменению (сначала недавно изменённые).
   Название и временные отметки должны приходить из backend, чтобы список
   оставался тем же после перезапуска и на других устройствах владельца.

### 4.2 Сохранение

1. Черновик создаётся в backend при явном создании или успешном импорте и
   сохраняется между маршрутами и перезапусками приложения, пока пользователь
   явно его не удалит согласно ADR-002.
2. Сохранить текущую возможность автосохранения, но показывать рядом с
   названием состояние: «Есть изменения», «Сохраняю…», «Сохранено» или
   «Не удалось сохранить» с повтором операции.
3. Добавить явную команду «Сохранить черновик», которая отправляет все
   текущие несохранённые изменения, включая название и каждый блок. Успех
   показывать только после ответа backend; ошибка не должна очищать введённый
   текст.
4. Переход к другому маршруту не должен терять введённые изменения: перед
   переходом фронтенд завершает сохранение либо предупреждает о невозможности
   сохранить и позволяет остаться на странице.
5. Если редактирование сохранено, повторное открытие черновика показывает
   именно сохранённые значения.

### 4.3 Статусы и действия

1. Показывать пользователю русские названия статусов, а не enum:
   `needs_user_review` — «Нужно проверить», `reviewed` — «Проверено»,
   `partially_applied` — «Часть данных перенесена», `applied` — «Данные
   перенесены».
2. Добавить явную кнопку «Отметить проверенным». Она доступна после успешного
   сохранения и вызывает существующую review-команду. После успеха черновик
   получает статус «Проверено», остаётся доступным в списке «Проверено» и
   открывается для просмотра.
3. Проверка означает только, что пользователь просмотрел черновик. Она не
   переносит данные в общую базу кандидата. Любой перенос должен быть отдельным
   явно подписанным действием и показывать, какие записи будут добавлены.
   Полный интерфейс преобразования текста в типизированные записи общей базы
   в этот fix не входит.
4. Статус проверки и прогресс переноса — разные понятия. Интерфейс должен
   показывать их раздельно, чтобы статус `reviewed` не выдавался за статус
   переноса и наоборот. Прогресс переноса получать из записей применения
   блоков, если этот индикатор включён в список.
5. Несохранённые изменения блокируют действие «Отметить проверенным» до
   завершения сохранения. Ошибка сохранения оставляет черновик в прежнем
   статусе.

### 4.4 Редактор блоков

1. Сохранить согласованное для REQ-056 представление каждого раздела отдельной
   широкой читаемой карточкой.
2. Каждый блок опыта показывать отдельной карточкой с нумерацией. Повторное
   добавление места работы создаёт ещё один редактируемый блок; старые блоки
   не заменяются. Рядом с формой явно указать, что можно добавить несколько
   мест работы.
3. Нераспознанный текст обозначать понятной подписью, сохраняя его содержимое
   без автоматической классификации или переписывания.

### 4.5 Личные разделы профиля

1. В редакторе каждого профиля показать карточки «Имя пользователя»,
   «Контакты» и «Обо мне».
2. Название специализации подписать отдельно, например «AI Engineer»; оно не
   должно отображаться как имя кандидата.
3. Контакты показывать отдельными полями с типом. Они являются общими
   записями кандидата; изменение отображается во всех его профилях и не
   меняет факты опыта или черновики.
4. «Обо мне» сохранять как краткое описание профиля и показывать при его
   повторном открытии.
5. Не заполнять имя, контакты или описание автоматически из VK-аккаунта,
   имени файла либо непроверенного содержимого импорта.

## 5. Требования к API и хранению

- Расширить DTO списка и чтения черновика полями `title`, `created_at`,
  `updated_at` и статусами, нужными списку. Точные имена сверить с
  существующими Pydantic-схемами при реализации.
- Добавить owner-scoped изменение названия черновика и атомарное сохранение
  его метаданных/нескольких блоков либо эквивалентную гарантию завершения всех
  изменений до ответа «Сохранено».
- Расширить CandidateBase и связанные DTO/API для имени кандидата; использовать
  типизированные контактные записи общей базы. Показать их в отдельных блоках
  профиля вместе с `summary` как «Обо мне». Поле `Profile.name` (название
  специализации) не используется вместо имени кандидата.
- При необходимости добавить колонку названия и Alembic-миграцию. Существующие
  записи должны получить уникальные пользовательские названия по дате
  создания и продолжить открываться по прежнему ID.
- Изменить список так, чтобы `reviewed` не терялся: он включается в общий
  список и может фильтроваться по состоянию.
- Сохранять owner scoping и мягкое удаление. Не возвращать исходный PDF/DOCX
  и не записывать содержимое резюме/персональные данные в логи.

## 6. Критерии приёмки

1. Пункты меню однозначно различают профиль специализации и черновик резюме;
   интерфейс объясняет, что такое профиль и что документ резюме ещё нужно
   сформировать.
2. После создания пустого черновика, импорта PDF/DOCX и добавления нескольких
   блоков опыта пользователь видит их в списке с разными названиями и датами.
3. Пользователь может уйти на другой пункт навигации, вернуться через пункт
   «Черновики резюме», выбрать прежний черновик и увидеть его сохранённые
   блоки и метаданные.
4. Непроверенный, частично перенесённый, перенесённый и проверенный черновики
   доступны через общий список/фильтры, если они не помечены удалёнными.
5. После редактирования название или текста состояние сохранения проходит
   через корректные состояния; успешное подтверждение соответствует данным,
   заново прочитанным с backend. Ошибка сохраняет локальный ввод и предлагает
   повтор.
6. «Отметить проверенным» доступно только после успешного сохранения;
   результат сохраняется после перезагрузки страницы и остаётся в списке
   проверенных.
7. Статус «Проверено» не утверждает, что данные перенесены в общую базу.
   Редактор и карточки не изменяют общую базу сами по себе.
8. Технический UUID не является основным видимым идентификатором черновика.
9. Повторное добавление опыта создаёт отдельные нумерованные карточки; правка
   одной не меняет соседние.
10. Редактор профиля показывает отдельные карточки имени человека, контактов
    и текста «Обо мне»; изменение одной карточки не меняет название
    специализации.
11. Изменение имени кандидата или общей контактной записи видно во всех
    профилях; оно не меняет названия специализаций и блоки черновиков.
12. Имя кандидата в профиле не подменяется названием специализации или именем
    учётной записи.
13. Существующие черновики после миграции сохраняют блоки, владельца,
    статус, историю и доступность; тестируется переход со старой схемы.

## 7. Границы и принятое решение

В объём входят термины и навигация, список всех сохранённых черновиков,
идентификация/переименование, явная обратная связь сохранения, пользовательская
команда проверки, локализованные статусы и миграция метаданных при
необходимости.

В объём не входят генерация или экспорт готового резюме, автоматическая
классификация фактов, физическое удаление, а также интерфейс подтверждённого
переноса произвольного текста в типизированную общую базу кандидата. Проверка
и перенос данных остаются разными операциями.

Решение Q-011: любая сохранённая правка проверенного черновика, включая
переименование, изменение или добавление блока, сбрасывает проверку и меняет
состояние на «Нужно проверить». Основание — прямой ответ пользователя в чате
2026-09-28: «Да, после любой правки снова “Нужно проверить”». Черновой статус
этого ТЗ сохраняется до отдельного review самого документа; реализация
разрешена поручением «выполняй» после уточнения поведения.
