# Дизайн интеграции LLM-провайдеров

## Назначение

Пользователь передаёт описание вакансии вручную или выбирает вакансию из
приложения, указывает специализационный профиль и запускает подготовку
отклика. Backend обращается к выбранному пользователем LLM-провайдеру и
создаёт отдельную версию, содержащую анализ требований, адаптированное
резюме, сопроводительное письмо, пробелы и вопросы. Пользователь может
редактировать и копировать документы; отправка работодателю выполняется вне
приложения.

Использование GPT CV Maker прекращается. Сервис подключает модели через API,
а не через сайт ChatGPT. Провайдер выбирается пользователем из подключённых
им интеграций.

## Основание и границы

- Пользовательское решение в чате от 2026-09-28: заменить кастомный GPT
  интеграцией по API и поддержать OpenAI-совместимый формат, YandexGPT и
  GigaChat.
- Пользовательское решение в чате от 2026-09-28: каждый пользователь
  подключает собственные учётные данные провайдера.
- Пользовательское решение в чате от 2026-09-28: версия под вакансию
  сохраняется отдельно; пользователь копирует готовый комплект и отправляет
  его вне приложения.
- Реальная пользовательская авторизация в текущем backend не подключена.
  Перед многопользовательским выпуском провайдерские подключения должны
  использовать подтверждённую идентичность пользователя; dev identity не
  считается production-аутентификацией.

В первом целевом сценарии поддерживается генерация текста через Chat
Completions. Эмбеддинги, изображения, вызовы инструментов, аудио, batch API,
автономная работа с Responses API и автоматическая отправка откликов не входят
в этот дизайн.

## Рассмотренные варианты

1. Один универсальный OpenAI-compatible адаптер. Прост в поддержке и подходит
   для совместимых endpoint, но не выражает различия аутентификации и
   возможностей отдельных провайдеров.
2. Отдельная бизнес-логика для каждого поставщика. Учитывает API полностью,
   но дублирует подготовку запросов и обработку результатов.
3. Общий внутренний контракт генерации с транспортными/аутентификационными
   адаптерами для OpenAI-compatible API, YandexGPT и GigaChat. Выбранный
   вариант сохраняет общую логику документов, а различия API остаются внутри
   адаптеров.

## Архитектура

```text
Frontend
  ├── управление подключениями пользователя
  └── создание/просмотр/редактирование версии отклика
          │
          ▼
FastAPI: owner-scoped API
  ├── LLM Connection Service (валидация endpoint, шифрование секретов)
  ├── Application Version Service (вакансия + снимок профиля + документы)
  └── Document Generation Service
          ├── Provider-neutral request/response contract
          ├── OpenAI-compatible adapter
          ├── Yandex AI Studio adapter
          └── GigaChat adapter
```

Каждый адаптер принимает внутренний запрос генерации и возвращает нормализованный
текст, сведения об использованной модели и usage, если поставщик их вернул.
Промпты, сбор данных кандидата, проверка результата и сохранение версии не
зависят от конкретного поставщика.

### Подключение провайдеров

- **OpenAI и OpenAI-compatible:** для OpenAI используется официальный API
  endpoint, модель и личный API key. Для совместимых endpoint пользователь
  задаёт HTTPS base URL, идентификатор модели и свой API key. Список моделей
  можно указать вручную; проверка подключения выполняет небольшой тестовый
  запрос.
- **YandexGPT / Yandex AI Studio:** подключение принимает API key сервисного
  аккаунта и folder ID; модель задаётся URI модели Yandex. Адаптер использует
  доступный OpenAI-compatible Chat Completions интерфейс и передаёт
  провайдерскую авторизацию. Поддержка IAM токена может быть добавлена
  отдельным способом аутентификации, если это потребуется пользователям.
- **GigaChat:** пользователь задаёт ключ авторизации и scope API. Адаптер
  получает ограниченный по времени access token, кэширует его до истечения и
  обновляет по необходимости, затем вызывает текстовый Chat Completions API.
  Совместимость частичная, поэтому начальный контракт не зависит от
  инструментов, расширенного JSON Schema или иных неподдерживаемых полей.

Пользователь может сохранить несколько подключений, выбрать модель для
конкретной генерации и задать подключение по умолчанию. Непроверенное либо
отключённое подключение нельзя использовать для генерации.

При сохранении подключения интерфейс объясняет, что при подготовке документов
выбранному провайдеру будут переданы описание вакансии и выбранные факты
профиля. Перед каждым запуском выбранный провайдер и модель видны пользователю;
автоматически переключать подключение при ошибке нельзя.

Секреты никогда не передаются frontend после сохранения, не включаются в
логи или трассировки и шифруются на сервере. Проект должен предоставить ключ
шифрования через секреты окружения/secret manager. Endpoint OpenAI-compatible
проверяется на HTTPS и блокирует loopback, private/link-local адреса и
опасные перенаправления, чтобы не допустить SSRF.

### Генерация версии отклика

1. Пользователь вводит текст вакансии или выбирает сохранённую вакансию,
   выбирает специализационный профиль, провайдера/модель и режим длины письма
   (150–300 слов или 800–1500 символов).
2. Backend проверяет владельца вакансии, профиля и подключения; выбирает
   только подтверждённые факты и допустимые формулировки профиля.
3. Backend сохраняет отдельную версию отклика со снимком использованных
   входных данных и запускает генерацию с выбранным подключением.
4. Система получает анализ вакансии, список соответствий и пробелов,
   уточняющие вопросы, текст адаптированного резюме и сопроводительного
   письма.
5. Детерминированная проверка связывает заявления документов с подтверждённой
   базой фактов. Неподтверждённые или не сопоставленные утверждения отмечаются
   для проверки пользователя и не добавляются в базу кандидата.
6. Пользователь просматривает, редактирует и сохраняет документы как новую
   редакцию версии, затем копирует их для отправки вне приложения.

Текст вакансии считается недоверенными данными и не может переопределять
инструкции системы, выбирать другой профиль или провайдера, обращаться к
инструментам либо изменять базу кандидата.

### Версии и сохранение

Каждая версия связана с владельцем, выбранным профилем, вакансией или
пользовательским текстом вакансии, параметрами письма, идентификатором
подключения, моделью, версией шаблона и происхождением использованных фактов.
Повторная генерация создаёт новую редакцию; предыдущий результат сохраняется.
Редактирование созданного документа не изменяет профиль или ExperienceBase.

Полные prompts и ответы провайдера не записываются в технические логи.
Сохранение содержимого самой версии отклика является пользовательской
функцией и регулируется политикой хранения документов. Требования аудита
Q-006 к полному prompt/result остаются открытыми.

## Ошибки и ограничения

- Ошибки подключения, истёкший/отозванный ключ, недоступная модель, квота,
  timeout и невалидный ответ показываются пользователю с безопасным описанием.
- Секреты и содержимое резюме не включаются в текст ошибки.
- Ошибка генерации не изменяет подтверждённый профиль и не сохраняет
  неполный комплект документов как готовый результат.
- Повтор запроса не должен молча создавать несколько одинаковых версий;
  команда генерации должна быть идемпотентна по request ID.
- Смена провайдера или модели не меняет уже созданные документы.

## Критерии проверки дизайна

1. Один внутренний генерационный контракт покрывает Chat Completions и
   нормализует текстовые результаты поддерживаемых адаптеров.
2. OpenAI-compatible подключение конфигурируется endpoint, моделью и личным
   ключом; YandexGPT и GigaChat имеют необходимые provider-specific поля и
   авторизацию.
3. Секреты изолированы по пользователю и не возвращаются клиенту после
   сохранения.
   До отправки данных пользователь видит, какой провайдер получит вакансию и
   выбранные факты профиля.
4. Вакансия и выбранный профиль образуют отдельную версию документов;
   перегенерация создаёт новую редакцию.
5. Резюме/письмо создаются только из подтверждённых фактов; результат
   не изменяет базу кандидата; неизвестные сведения становятся вопросами.
6. Пользователь может редактировать и копировать документы; отправка из
   приложения отсутствует.
7. Перед production многопользовательским запуском подключена реальная
   аутентификация; local dev identity недостаточна.
8. Ошибки и аудит не раскрывают API keys, полный prompt или полные ответы.

## Открытые вопросы

- Q-006: состав аудита, хранение и доступ к содержимому запроса/ответа.
- Q-010: точная политика удаления провайдерского подключения и криптографического
  секрета с учётом принятого для MVP мягкого удаления доменных записей.
- Production identity: текущая реализация не подключает запланированные
  Yandex ID/VK ID. Реализация генерации должна оставаться за пределами
  многопользовательского production до завершения аутентификации.
