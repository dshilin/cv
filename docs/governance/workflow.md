# Правила ведения документации

## Ответственность и согласование

Агент готовит и проверяет изменения в рамках задания. За продуктовые цели,
границы и бизнес-требования отвечает пользователь/владелец продукта;
персональные назначения остальных ролей пока отсутствуют. Владелец
документа организует актуализацию и рассмотрение; роль не означает
назначение конкретного человека. При передаче проекта назначаются реальные
владельцы и получатели эксплуатационной документации.

Для продуктовых спецификаций используются `draft` → `in_review` →
`approved` → `superseded` или `archived`. Возврат с проверки — в `draft`.
Для служебных реестров и правил используется `active`. Утверждение
фиксируется именем/ролью, датой, версией и ссылкой либо точной формулировкой
решения из задания. Отсутствие ответа не означает согласования.

Запрос пользователя уже разрешает описанное в нём действие. Для обратимых
правок, организации файлов и проверок отдельное подтверждение не требуется.
Если содержание неоднозначно, агент уточняет только зависимую часть и
продолжает остальную работу. Не выдаёт собственную интерпретацию за согласие.

## Цикл задачи

| Этап | Действия | Условие перехода |
|---|---|---|
| Изучение | Прочитать карту, состояние, вопросы и релевантные источники | Известны цель, границы и исходные критерии |
| Подготовка | Связать задачу с требованиями; отметить допущения и зависимости | Нет нерешённого вопроса, блокирующего выбранную часть |
| Выполнение | Изменить реализацию и затронутые документы в одной задаче | Поведение и описание согласованы |
| Проверка | Выполнить критерии приёмки, проверки кода и документации | Есть результаты либо явно названный блокер |
| Завершение | Обновить связи, состояние и отчёт | Результат проверяем другим участником |

## Формат и качество

Все рабочие документы — Markdown UTF-8/LF с реквизитами из
[шаблонов](templates.md). ID документа и требования остаётся стабильным
при переименовании. Названия файлов отражают назначение, без final/final2.
Внутренние ссылки относительные; внешние — с понятным названием источника.
Одинаковые сущности называются одинаково; несовместимые термины сначала
фиксируются как вопрос, затем согласованно меняются во всех источниках.

Одно новое требование описывает одну проверяемую потребность: условия,
поведение, исключения и критерий приёмки. Указывается источник. Неизвестные
значения и допущения обозначаются явно. Текст не дополняется выдуманными
фактами, метриками, согласованиями или результатами тестов.

## Изменения и версии

Для изменения фиксируются причина, основание, затронутые требования,
документы, реализация и проверки. Существенное изменение архитектуры
получает ADR; небольшая правка — строку в состоянии проекта или описание
коммита/задачи. Готовый результат предъявляется перед отдельным действием,
для которого действительно необходимо разрешение.

Версии: `0.x` для нового черновика; `1.0` для первой принятой редакции;
минорная версия для оформления/уточнения без изменения смысла; мажорная —
для изменения поведения. Статус согласования независим от номера версии:
унаследованная версия 1.0 не означает `approved`.

При изменении утверждённого содержания прежняя редакция сохраняется,
новая получает `draft` или `in_review` до подтверждения. Предпочтительна
история Git, когда репозиторий будет настроен. Сейчас `.git` отсутствует;
не считай файлы уже закоммиченными. До подключения Git сохраняй заменяемую
существенную редакцию в архив с датой и записью в его реестре. Не создавай
резервные копии на каждую опечатку.

## Связи и критерии завершения

Поддерживается цепочка: цель → требование → задача → реализация → проверка.
Используется [реестр критериев](../requirements/traceability.md).
Ссылка на задачу или тест добавляется только после их реального появления.
Незаполненная связь помечается «не создано», а не вымышленным URL.

Задача завершена, когда достигнут запрошенный результат, документация
соответствует изменению, локальные ссылки действуют и применимые проверки
пройдены. `python scripts/check_docs.py` запускается из корня проекта.
Тесты приложения выбираются по изменению после появления реализации;
не придумывай команды сборки. Проверка структуры документов не доказывает
согласованность бизнес-требований.

## Актуализация и исключения

Обновляй документацию при изменении требований, поведения, API, схемы
данных, запуска или эксплуатации и перед передачей результата. Для
длительных задач записывай прогресс после завершённых этапов. Не полагайся
на память предыдущей сессии.

Для командного процесса предлагаются сроки: протокол и принятое решение —
один рабочий день; первичное рассмотрение — три рабочих дня; обзор активных
документов — ежемесячно и перед релизом. Это организационные ориентиры:
они не создают расписаний, фоновых задач или обязательств согласующих без
назначения ответственных. В работе агента документы обновляются до сдачи.

Исключение фиксируется с причиной, риском, ответственным, сроком и
основанием разрешения. Просрочки и неразрешимые расхождения отражаются в
открытых вопросах и сообщаются пользователю. При завершении проекта
передаются итоговые документы, сведения о проверках и оставшиеся вопросы.

## Доступ и источники

Markdown использует права файловой системы/репозитория; отдельные ACL
этой задачей не настроены. Не помещай в документацию ключи, токены,
реальные резюме и ненужные персональные данные. Внешние отправки требуют
соответствующего поручения; настройка правил не даёт его автоматически.
